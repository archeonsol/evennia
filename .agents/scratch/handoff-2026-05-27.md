## The actual blocker: production deploy failing on `.22`+

We do **not** know the root cause yet. The systemd exit-1 reported from


Whatever line that surfaces is the real fire. Everything else below is
speculation or hygiene.

### Highest-likelihood candidates, in case the log narrows fast

Best to confirm against the actual log before acting on any of these.
Listed in rough order of "this would manifest as systemd exit-1 with
no obvious server-side trace":

1. **`scripts/0018_scriptdb_pause_fields_and_start_delay_secs.py` not
   applied on the production DB.** Migration shipped in commit
   `ebeb03e8f`. If the deploy script skipped `evennia migrate`, every
   ScriptDB read raises `OperationalError: no such column
   scriptdb.db_paused_time` at startup and the service exits before
   it produces a useful in-game log line.
2. **Removed module-level constants** `_MAX_SERVER_COMMANDS_PER_SECOND`
   and `_MAX_SESSION_COMMANDS_PER_SECOND` in
   [`evennia/server/sessionhandler.py`](../../evennia/server/sessionhandler.py).
   Engine grep is clean across `evennia/`, but newmoo may import them.
   If so, `ImportError` at module load → service won't start.
3. **Lock-eval replacement** in
   [`evennia/locks/lockhandler.py`](../../evennia/locks/lockhandler.py).
   `eval()` was replaced with a hand-rolled boolean parser
   (`_eval_bool_expr`). It only accepts `True`/`False`/`and`/`or`/
   `not`/parens. If any production lockfunc returns something that
   stringifies to anything else after substitution, the parser silently
   returns `False` and the command/access check fails closed. Won't
   show as exit-1 but would explain "service starts but feels stuck"
   reports.
4. **Async/await mismatches in shutdown path.** `ebeb03e8f` made
   `EvenniaServerService.shutdown()` `async`; `22fd8eb86` patched the
   three AMP handlers (`SRELOAD`, `SRESET`, `SSHUTD`) to wrap in
   `defer.ensureDeferred`. If any other call-site of `shutdown()` was
   missed, the coroutine gets created and discarded and shutdown never
   runs — could cause hangs during `@reload` from in-game.

If the log points elsewhere, ignore this list.

## Migration drift — benign, deferred

Downstream review of `.22` surfaced unrecorded model changes in three
apps: `world` (downstream), `server` (engine), `typeclasses` (engine).

**Important context from downstream investigation:** the drift was
already present at `.19`, which deployed successfully. Same `Tag.Meta`
declaration, same migration head (`0019` in both `.19` and `.22`). The
drift is **real but benign** — `migrate` exits clean with a warning,
the indexes exist on disk under their historical (Django 5.x) names,
nothing breaks at runtime. So this is hygiene, not a deploy blocker,
and the original "missing migrations broke `.22`" theory is ruled out.

### Engine work still owed

When time allows, two follow-up migrations for a future tag (`.25`?):

- **`server` app:** straight `makemigrations server` output. Migration
  alters `id` from `AutoField` → `BigAutoField` on `gameevent` and
  `enginejob` (the existing `0004_gameevent_enginejob` predates
  [`settings_default.py:381`](../../evennia/settings_default.py) setting
  `DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"`), and renames
  the `gameevent.subject_created_at` index from `_0e8f0d_idx` to
  `_40e896_idx` (Django-version hash mismatch). Safe to take as-is.
- **`typeclasses` app:** **not** safe to auto-generate. Django's
  autodetector proposes
  `RemoveIndex typeclasses_tag_db_key_db_category_db_tagtype_db_model_idx`
  — accepting that would drop the index on every deployed DB. Correct
  fix is to confirm the actual on-disk index name on production
  (`SELECT indexname FROM pg_indexes WHERE tablename = 'typeclasses_tag'`)
  and write a `migrations.SeparateDatabaseAndState` migration that
  updates Django's recorded state to match without touching schema.

`.23`'s Django exact-pin prevents *new* drift but doesn't fix these
existing entries. Both are low-priority — they nag but don't break.

**not** committed. With the known-benign drift currently in `server`
and `typeclasses`, the check would fail every PR until the two

ignore the failure.

1. Land the `server` migration.
